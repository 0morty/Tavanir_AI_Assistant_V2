# Generation API pipeline validation

## 1. Executive Summary

**Overall assessment: partial component validation; the requested API-to-generated-response lifecycle is not implemented end to end.** The deterministic Generation checks passed, but `/api/v1/suggestions/analyze` returns a prepared prompt as `analysis` and does not call a final LLM, parse its result, or resolve its citations. The current test environment also cannot run the HTTP stack or a live model.

- Executed: 30 focused `unittest` test methods, 30 passed, 0 failed, 0 errors. The existing ten-chunk trace test additionally evaluated 33 named assertions, all passed. Python's `unittest` does not report a total count of assertion calls in the remaining methods; no total is inferred.
- Warnings/limits: 3 material gaps — missing final Generation orchestration, unavailable HTTP/runtime dependencies, unavailable live provider/model tokenizer.
- Validated by execution: section ordering and rendering, deterministic collection citations, reference injection, allocation, overflow strategy dispatch, batched per-item summarization, truncation, whole-item ignore, LLM request serialization, deterministic raw-response extraction and citation resolution.
- **Not validated:** a real `/suggestions/analyze` request through a live stack, production model inference, model-token accounting, structured-output validation in the API, and a public response containing only citations selected by the model.

The complete executed ten-chunk ContextBuilder trace, including all per-item inputs, prompts, outputs, capacities, and the exact final request body, is in [context_builder_trace.md](context_builder_trace.md). It was generated by the existing test with `CONTEXT_BUILDER_FINAL_REPORT_PATH=tests/integration/reports/context_builder_trace.md` and is complementary evidence for this assessment.

## 3. Test Scenario

The main executed trace uses ten original `GenerationChunk` objects, `SUG-001` through `SUG-010`, each with three English evidence paragraphs and a structured study/page `Reference`. The subject is household daylight, lighting controls, and adjacent energy proposals. Sections are ordered `ROLE → CHUNKS → SYSTEM-INPUT → OUTPUT-FORMAT`. Budget: 2,800 character tokens. The CHUNKS stack is `SUMMARIZE → TRUNCATE → IGNORE`, with a batched scripted summary for each item. The reference-template generator used one scripted completion and a shape-hash cache for all ten references.

A separate three-chunk scenario includes all five supported non-history sections, including `USER-INPUT`. It explicitly instructs the model to preserve `Reference` and `Unique ID`, requests JSON with `answer` and `citations`, and manually invokes a scripted `ILLMClient`. Budget: 945 character tokens; final prompt: 933; remainder: 12. This manual invocation tests the components' seams, not API integration.

The public `AnalyzeSuggestionRequest` accepts a current suggestion (`title`, `currentProblem`, `solution`, optional `contextTitle`). It does not accept this prebuilt `PromptBuilder` or the three-chunk list directly. The use case itself retrieves and prepares similar suggestions. Its configured prompt path uses `SimilarSuggestionsSection`, not `ChunksSection`. Regulations are present in `GenerationInput` but the observed `SuggestionPromptPreparer` does not add a regulations section. No regulation-fetch behavior was assumed.

## 5. ContextBuilder Analysis

- **Creation and rendering:** `ChunksSection` is a `ReferencedCollectionSection`. It assigns IDs at construction and prepares one independent input per original chunk. A rendered body is:

  ```text
  There is a title "Light shelf and clerestory study" on page 14:
  Unique ID: [chunk 002]

  Light shelves and clerestories spread daylight with pale interior finishes.
  ```

  This exact final content came from the ten-chunk summary trace. No `Chunk N:` report label was present in the tested LLM-facing content or summarization prompts.

- **Allocation and strategy choice:** CHUNKS had demand 0.50 and importance 0.90. Its initial 1,397 tokens plus 377 redistributed tokens yielded 1,774. `SUMMARIZE` was first in its configured strategy stack and produced 1,591 tokens, so ContextBuilder selected it. `TRUNCATE` and `IGNORE` were not attempted in this run. ROLE, SYSTEM-INPUT and OUTPUT-FORMAT needed 282, 393 and 345 tokens respectively and remained intact.
- **Summarization transformation:** For `SUG-001`, the prepared per-item input was 667 characters. The scripted summary was `Orient rooms and windows to carry daylight inward and reduce lamp use.` The rewrapped per-item output was 183 characters, saving 484. Its reference remained `There is a title "Orientation and daylight layout" on page 12:` and its ID remained `[chunk 001]`. `SUG-002` went from 640 to 189, saving 451. The summary strings did not supply either reference or ID; the collection reattached them from the original item mapping.
- **Truncation:** A single `SystemInputSection` with budget 18 produced the exact 18-character prefix of its prepared text. This was a character-boundary cut, as designed. `ChunksSection.truncate` returned the original prepared result unchanged; ContextBuilder then used `IGNORE` for a collection that still overflowed.
- **Ignore:** With capacity equal to the complete rendering of only the first chunk, the result retained `[chunk 001]`, removed chunks 2 and 3, and rejected resolution of `[chunk 002]`. This is whole-item trailing removal. The corresponding original source remains in the collection's full map but is absent from `citation_map_for` the fitted result.
- **Unresolvable overflow:** The exposed standard strategies can produce an empty result at zero capacity; no normal-tokenizer scenario in these checks reached the `Section ... cannot fit capacity` guard. This edge was not claimed as tested.

The full input/output and token impact for each of the ten summarized items, including each independent `complete_many` prompt, is preserved in the companion trace.

## 7. LLM Analysis

**Observed fact — request builder:** The ten-chunk ContextBuilder result serialized to an OpenAI-compatible request dictionary with one `system` message, `model='generation-test-model'`, `temperature=0.2`, and `max_tokens=256`. The exact message content and complete JSON body are in the companion trace, section 14. Its prompt contained all ten `Reference` renderings and `Unique ID` markers. That system instruction said `cite each Unique ID`. The separate three-chunk test additionally used the literal instruction `Preserve Reference and Unique ID` and verified it reached the message.

**Observed fact — deterministic final-completion seam:** The three-chunk test manually called a scripted `ILLMClient.complete(result.prompt)`. The raw response was:

```json
{"answer": "Light shelves and daylight controls are related approaches.", "citations": ["[chunk 002]", "[chunk 003]", "[chunk 002]"]}
```

`json.loads` yielded a mapping, `extract_citation_ids` removed the repeat, and `resolve_citation_ids` selected only the two originals. Raw response format was scripted JSON text. No provider token usage or generation metadata was available. The raw string contains 133 Unicode characters in this test; that is not a provider output-token count.

**Expected behavior:** A complete API path would invoke a configured final model, validate a structured answer, map cited IDs against the fitted collection, and return cited originals only. **Inference from source inspection:** The current API cannot do this because the use case ends after `SuggestionPromptPreparer.prepare` and constructs `AnalyzeSuggestionResponse(analysis=prompt_result.prompt, ...)`. No final `LLMRequestBuilder`, `ILLMClient.complete`, `json.loads`, `extract_citation_ids`, or `resolve_citation_ids` call occurs in the router/use-case path.

Malformed JSON raised `JSONDecodeError` in the manual test. Missing or non-list `citations` and malformed citation strings raised `ValueError` in the collection method. An empty `citations` list was accepted. There is no integrated final-output parser to validate an `answer` field or convert provider failures into a public Generation error on this endpoint.

## 10. Findings

### Critical

None established.

### High

1. **Final Generation stage is absent from the analyze endpoint (high confidence).** The use case's Step 12 prepares a prompt and returns it as `analysis`. A caller receives prompt text in the generated-analysis field, with no final model response. This blocks the requested end-to-end validation and the advertised decision-support answer.
2. **Public similar-suggestion IDs are not model-cited references (high confidence).** The use case builds `similar_*_ids` from hydrated retrieval partitions before any final model call. The public schema has no citation-ID/resolved-reference field. Returning those IDs as evidence actually used by a model would be incorrect. The manual collection test proves the available mapping can distinguish supplied evidence from cited evidence, but no API code uses it.

### Medium

3. **Structured final-output contract is not enforced on the API path (high confidence).** There is no final parser invocation in the use case. `ReferencedCollectionSection.extract_citation_ids` validates only a `citations` list and accepts a mapping without `answer`; it is a local extraction utility, not full output validation. Malformed/missing answer handling and provider failure mapping at the public boundary remain undefined in executable code.

### Low

4. **Prompt preservation wording differs by path (medium confidence).** The tested ten-chunk system text asks for each `Unique ID` but does not explicitly say to preserve the `Reference` and `Unique ID` markers. The separate custom three-chunk test includes that wording. The collection itself preserves the markers through summarization regardless of model output; this is a prompt-contract observation, not a demonstrated citation-loss defect.

### Informational

5. The main trace did not enter TRUNCATE or IGNORE because SUMMARIZE already fitted. Focused tests separately exercised those strategies. No test inferred that truncation must preserve semantic boundaries.
6. The executed request dictionary is constructed by `LLMRequestBuilder`, but the active analyze use case does not use that builder. No actual wire request was sent to an LLM provider. `OpenAILLMClient.complete(prompt)` constructs a single `user` message itself, so this request-builder dictionary is not the wire shape of that adapter; the final message contract must be settled when orchestration is implemented.

## 11. Recommendations

| Problem | Evidence / root cause | Impact | Recommended fix and why |
|---|---|---|---|
| Prompt returned as analysis | `AnalyzeSuggestionUseCase.execute` returns `analysis=prompt_result.prompt` after preparation | No generated answer | Wire a final `ILLMClient` call after prompt preparation, then return its validated answer. This is required for the endpoint's Generation contract. |
| Supplied IDs treated as final provenance | `similar_*_ids` are populated from retrieval partitions before generation | Cannot identify evidence actually cited | Resolve IDs from the final model's citation list against the *fitted* collection mapping and expose a separate cited-reference result. Preserve existing retrieval IDs only if their meaning is explicit in the response contract. |
| No final structured-output validation | Collection extractor validates citations only; no API parser call | Malformed answers and unknown/removed citations are not handled publicly | Define the final output schema and parser, validate `answer` and citations, reject or explicitly handle malformed/unknown IDs, and map provider/parser errors through Generation-specific response handling. |
| Live runtime evidence unavailable | Required Python packages absent; localhost:8000 unavailable | HTTP, real model behavior, and model-token budget not validated | Run the existing API integration suite and a controlled provider test in the project's configured environment, recording actual model name, tokenizer, request, response, usage, and public HTTP result. |

These are recommendations only. No production behavior or out-of-scope code was changed.

## 12. Final Assessment

The deterministic component behavior is well supported by fresh tests: references and short IDs are rendered correctly, IDs remain attached to original items after summarization, whole-item removal narrows eligible citations, malformed/unknown IDs are rejected, and request serialization preserves the fitted prompt. The ten-chunk ContextBuilder trace and the three-chunk manual citation path provide reproducible intermediate evidence.

The complete Generation API **cannot be considered fully validated**. Its current analyze endpoint does not perform final inference or citation resolution, the HTTP stack was unavailable here, and no live model or model tokenizer ran. The 30 passing tests establish only the components and manually composed seams listed above. No failed test was hidden or converted into a pass; the unimplemented and unavailable stages remain explicit findings and limitations.
